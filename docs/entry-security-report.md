# Lot 11 — Points d'entrée et abus : livraison partielle

WSGI/ASGI utilisaient development par défaut. Ils utilisent maintenant production ; pour le local, fournir explicitement DJANGO_SETTINGS_MODULE=config.settings.development ou --settings sur manage.py. La production garde DEBUG=False, TLS, cookies Secure/HttpOnly, CSRF et les restrictions superuser existantes. Les domaines vides/jokers/domaines avec chemin sont refusés. Les variables déjà requises restent obligatoires.

La production exige DJANGO_SHARED_CACHE_BACKEND et DJANGO_SHARED_CACHE_LOCATION : RedisCache ou PyMemcacheCache seulement. Aucun service ni driver n'est supposé installé. Installer le driver correspondant dans l'environnement validé (redis ou pymemcache) avant démarrage ; définir les secrets hors dépôt. Aucun cache partagé n'a été contacté ou provisionné.

Le middleware limite, par adresse REMOTE_ADDR hachée avec secret serveur et fenêtre de cinq minutes, les POST login administration/gestion à 20, codes promo à 30, créations de paiement à 10. Ce sont des seuils techniques initiaux, non mesurés sur trafic réel ; ajuster après observation. Les devis asynchrones et le retrait de code sont exclus. Retour 429 avec Retry-After 300 ; panne du cache : 503, sans succès trompeur. Un proxy peut agréger plusieurs clients sous la même adresse : valider REMOTE_ADDR avant activation. Aucun X-Forwarded-For non fiable n'est accepté. Les limites sont activées uniquement dans production.

Panier, checkout, gestion, admin et favoris reçoivent private/no-store. CSP ajoutée en report-only : scripts locaux, styles inline existants et Google Fonts, images/médias HTTPS, Stripe hébergé. Aucune politique bloquante activée. Les sources externes doivent être inventoriées et les violations observées en navigateur avant restriction. Aucun endpoint collecteur de rapports n'est ajouté : pas de collecte de données client. Permissions-Policy désactive caméra, microphone et géolocalisation, sans bloquer explicitement payment. HSTS sous-domaines/preload restent désactivés.

Fichiers : config/wsgi.py et asgi.py (profil), config/settings/base.py (middleware), production.py (cache partagé et domaines), config/security.py (quotas/en-têtes), config/test_security.py (quota/reprise et report-only), .env.example (configuration documentée), README et ce rapport.

Commandes exécutées : manage.py check --settings=config.settings.development ; manage.py test dashboard checkout --settings=config.settings.development ; manage.py test config.test_security --settings=config.settings.development ; git diff --check. Secret local de test uniquement. Voir compte rendu final pour les nombres réellement passés. Les tests de quotas utilisent le cache local, pas plusieurs workers.

**Restant essentiel : expiration autonome des réservations non implémentée dans ce lot**, planificateur et durée à définir ; ne pas supposer qu'un retour navigateur ou un webhook libère toujours la réservation à temps. Il reste à implémenter/tester la tâche idempotente et sa concurrence sur la base réellement hébergée. Les réservations et leurs contrôles transactionnels existants n'ont pas été réécrits.

Autres vérifications restantes : échec de démarrage production sur variables manquantes, driver/cache réel, atomicité add/incr et quotas multi-processus, domaine/proxy/TLS, CDN no-store, parcours Stripe et collecte des violations CSP en préproduction. Aucun check --deploy ne démontre ces propriétés. Aucun en-tête observé en préproduction, capture navigateur ou largeur mobile vérifiée. Aucun déploiement, fusion ou paiement réel. Prix, stock, webhook signé, idempotence et CSRF conservés ; aucun secret/coordonnée ajouté aux journaux ou au stockage navigateur. Lot non entièrement validé et non entièrement terminé.

Résultat final exécuté : 117 tests dashboard/checkout/config.test_security réussis, 11,616 s ; Django check sans problème et diff sans erreur. Cela inclut les deux nouveaux tests du middleware. Aucune validation multi-processus n'est déduite de ce résultat.
